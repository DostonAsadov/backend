# Техническое задание и архитектура
## Интернет-магазин запчастей для электровелосипедов «Вольт Гараж»

---

## 1. Общее описание проекта

Интернет-магазин для продажи запчастей и аксессуаров для электровелосипедов (моторы, батареи, контроллеры, дисплеи, тормоза, аксессуары). Каталог 10–50 товаров, mobile-first интерфейс, личный кабинет покупателя (история заказов, баланс), оплата картой (Click / Payme), доставка оформляется на сайте, трекинг доставки реализуется отдельным внешним сервисом. Интерфейс на русском и узбекском языках. Полноценная админ-панель для управления каталогом, заказами и сотрудниками.

**Цель:** дать малому бизнесу простой, быстрый и недорогой в поддержке сайт, который можно запустить за 3–5 недель и расширять по мере роста.

---

## 2. Целевая аудитория

- Владельцы электровелосипедов в Узбекистане, нуждающиеся в запчастях и ремонте.
- Веломастерские, закупающие детали небольшими партиями.
- Энтузиасты, собирающие электровелосипеды самостоятельно.

## 3. Функциональные требования

### 3.1 Публичная часть (фронтенд, mobile-first)

| Раздел | Описание |
|---|---|
| Главная страница | Хедер, баннер/хиро, навигация по категориям, переход в каталог. Верстка проектируется сначала под мобильный экран (320–414px), затем масштабируется на планшет/десктоп |
| Переключатель языка | RU / UZ в хедере, хранится в профиле пользователя (поле `locale`, для гостей — в localStorage/cookie) |
| Каталог товаров | Список товаров с фильтрацией по категории, диапазону цены (`min_price`, `max_price`), сортировкой (`sort`) и поиском по названию/SKU |
| Карточка товара | Фото, название, SKU, описание, цена, наличие, кнопка «В корзину». Адрес страницы — по `slug` товара |
| Корзина | Хранится локально на фронтенде (Pinia + localStorage): добавление/удаление товаров, изменение количества, расчёт итоговой суммы |
| Оформление заказа | Только для авторизованного покупателя. Форма: имя, телефон, адрес доставки, способ доставки, комментарий; выбор способа оплаты (Click / Payme / баланс / наличные) |
| Доставка | Покупатель выбирает способ доставки и указывает адрес на сайте; трекинг ведётся во внешнем сервисе и не отображается в личном кабинете на 1-м этапе |
| Онлайн-оплата | Интеграция с Click и Payme (редирект на платёжную страницу или виджет) |
| Подтверждение заказа | Страница «Заказ принят» с номером заказа |
| Регистрация и вход | По номеру телефона + пароль (отдельные эндпоинты регистрации и входа) или через Telegram (Telegram Login Widget, без пароля). SMS-подтверждение номера на 1-м этапе не делается (см. раздел 8) |
| Личный кабинет | Профиль (имя, телефон, язык), история заказов со статусами, текущий баланс |
| Статичные страницы | О магазине, Контакты, Доставка и оплата, Политика возврата — на RU и UZ |

### 3.2 Административная часть (админка)

| Раздел | Описание |
|---|---|
| Авторизация | Email + пароль для сотрудников (1–3 человека). Публичной регистрации нет |
| Роли | PHP Enum `UserRole` в поле `role` таблицы `users`: `admin` (полный доступ) и `manager` (ограниченный доступ — уточняется, см. раздел 7). Разграничение через role-middleware |
| Управление сотрудниками | Супер-админ (создаётся сидером `AdminUserSeeder`) создаёт, редактирует и деактивирует пользователей `admin` / `manager` |
| Управление товарами | CRUD: название (RU/UZ), описание (RU/UZ), SKU, slug (генерируется автоматически), категория, цена, фото (несколько), остаток, активность |
| Управление категориями | CRUD категорий с названиями RU/UZ, поддержка вложенности (родительская категория) |
| Управление заказами | Список заказов, смена статуса, детали заказа, способ оплаты и её статус, адрес доставки |
| Уведомления | Уведомление о новом заказе в Telegram-бот менеджеру (через очередь) |
| Базовая статистика | Кол-во заказов за период, сумма продаж, топ товаров (опционально, после запуска) |

### 3.3 Нефункциональные требования

- **Mobile-first**: дизайн и верстка проектируются для мобильных экранов первично (320–414px), затем адаптируются под планшет/десктоп.
- Время загрузки главной страницы — не более 2 сек на 4G.
- Полная поддержка двух языков: русский и узбекский (переключение без перезагрузки страницы, контент товаров и категорий хранится в обеих локалях).
- HTTPS (Let's Encrypt), защита авторизации от перебора — rate limiting на эндпоинтах входа.
- Логирование платежных транзакций (сырой payload провайдера сохраняется в `payments.payload`).
- Резервное копирование базы данных ежедневно.

### 4.2 Технологический стек

| Слой | Технология | Обоснование |
|---|---|---|
| Backend | **Laravel 13** (PHP 8.4) | Зрелая экосистема, Eloquent ORM, встроенные миграции, очереди, готовые пакеты |
| Архитектурный паттерн | **Controllers → Services → Models** (слоистая, без модулей и CMS) | Контроллер только принимает запрос и возвращает ответ; вся бизнес-логика — в сервис-классах; вся валидация — в FormRequest |
| API-аутентификация | **JWT** (`php-open-source-saver/jwt-auth`) | Stateless-токены, удобны для SPA и потенциального мобильного приложения |
| Guards | Два независимых guard'а в `config/auth.php`: **`customer`** (модель `Customer`) и **`api`** (модель `User`) | Полная изоляция аутентификации покупателей и персонала |
| Контракты | Платёжные сервисы реализуют общий интерфейс `PaymentGatewayInterface` | Единый контракт для Click и Payme |
| Frontend | **Vue 3 + Vite + Vue Router + Pinia**, `vue-i18n` (ru/uz JSON) | Отдельный SPA (`/var/www/e-garage/frontend`), общается с Laravel только через REST API |
| База данных | **SQLite** локально, **MySQL 8** в продакшене | Быстрый старт в разработке, стандарт для продакшена |
| Очереди | **Laravel Queue на Redis** | Обработка вебхуков платежей, уведомления в Telegram |
| Хранение изображений | **Laravel Filesystem** — локальный диск на старте, S3 при росте | Абстракция через `Storage::disk()` |
| Платежи | Click и Payme — собственные сервис-классы `ClickPaymentService`, `PaymePaymentService`, реализующие `PaymentGatewayInterface` | Единый контракт для всех платёжных методов |
| Уведомления | Telegram Bot API | Уведомление менеджера о новом заказе |
| Хостинг | VPS (2 CPU, 4 GB RAM, 40 GB SSD), Docker: nginx, php-fpm, mysql, redis | Важно для скорости платёжных вебхуков |
| SSL | Certbot + Let's Encrypt | Бесплатный HTTPS |
| Деплой | GitHub Actions → VPS | Автоматизация миграций и сборки фронтенда |

> Frontend и backend деплоятся раздельно: Laravel — только JSON API и вебхуки, SPA раздаётся отдельно.

                            ▼
┌─────────────────────────────────────────────────────┐
│  Service  (app/Services)                             │

Сервис-классы: `CustomerAuthService`, `AdminAuthService`, `TelegramAuthService`, `ProductService`, `CategoryService`, `OrderService`, `ClickPaymentService`, `PaymePaymentService`.

Guard всегда указывается явно: `auth()->guard('customer')` или `auth()->guard('api')`. API отдаёт только JSON — `bootstrap/app.php` превращает `AuthenticationException` в ответ `401` без редиректа.

### 4.4 Аутентификация: два JWT-guard'а

```php
'guards' => [
    'api' => [
        'driver' => 'jwt',
        'provider' => 'users',       // App\Models\User (сотрудники/админы)
    ],
    'customer' => [
        'driver' => 'jwt',
        'provider' => 'customers',   // App\Models\Customer (покупатели)
    ],
],
```

Токен покупателя не подходит ни к одному admin-эндпоинту, и наоборот. Middleware на роутах: `auth:customer` для личного кабинета, `auth:api` для админки.

**JWT claims:**
- Покупатель: `{ type: "customer", sub: id, prv: hash(Customer) }`
- Сотрудник: `{ type: "admin", role: "admin"|"manager", sub: id, prv: hash(User) }`

**Покупатели (`guard: customer`).**
- Телефон + пароль → отдельные эндпоинты `register` и `login`, оба возвращают JWT.
- Telegram Login Widget → проверка `hash` от Telegram в `TelegramAuthService` → поиск/создание `Customer` по `telegram_id` → выпуск JWT.
- SMS-подтверждение номера на 1-м этапе не делается (см. раздел 8).

**Персонал (`guard: api`).** Модель `User` с полями `email`, `password`, `role` (enum `UserRole`: `admin`, `manager`). Публичной регистрации нет: супер-админ создаётся сидером `AdminUserSeeder`, остальные сотрудники — через `AdminUserController`.

**Время жизни токенов (`config/jwt.php`).**

| Параметр | Значение | Назначение |
|---|---|---|
| `ttl` | 15 минут | Время жизни Access Token (`Authorization: Bearer ...`) |
| `refresh_ttl` | 7 дней | Окно, в течение которого истёкший токен можно обменять на новый через `/refresh` |

Обновление и выход реализованы встроенными механизмами `jwt-auth` (refresh + blacklist), отдельная таблица для refresh-токенов не используется. Фронтенд автоматически обновляет токен через interceptor на ответ `401`.

### 4.5 Модель данных (миграции Laravel)

**users** (guard `api`, сотрудники)
- id, name, email (unique), password, role (enum `admin`/`manager`), is_active (bool, default true), timestamps

**customers** (guard `customer`)
- id, name, phone (nullable, unique), password (nullable, hashed), telegram_id (nullable, unique), telegram_username (nullable), locale (default `uz`), balance (decimal 12,2, default 0), timestamps

> Один из идентификаторов — `phone` или `telegram_id` — обязателен на уровне валидации. У покупателей, вошедших только через Telegram, `password` остаётся `null`.

**categories**
- id, parent_id (FK categories, nullable), name_ru, name_uz, slug (unique), timestamps

**products**
- id, category_id (FK), sku (unique), name_ru, name_uz, description_ru, description_uz, slug (unique, генерируется автоматически), price (decimal), stock (int), images (JSON — массив путей), is_active (bool), timestamps

> Переводы хранятся колонками `*_ru` / `*_uz` прямо в таблицах — для двух языков и 10–50 товаров это проще отдельных `*_translations`-таблиц. Если языков станет больше, можно вынести в `product_translations`.

**orders**
- id, customer_id (FK), status (enum, см. 4.7), total (decimal), delivery_address (JSON: имя, телефон, адрес, способ доставки, комментарий), payment_method (enum: click/payme/balance/cash), payment_status (enum: pending/paid/failed), timestamps

**order_items**
- id, order_id (FK), product_id (FK, nullable — товар могут удалить), sku, name_ru, name_uz (снимок товара), qty (int), price_snapshot (decimal — цена на момент заказа, **обязательно**, т.к. цена товара может измениться)

**payments**
- id, order_id (FK), provider (enum: click/payme), external_id (ID транзакции у провайдера), amount (decimal), status, payload (JSON — сырой ответ провайдера), timestamps

### 4.7 Поток заказа и оплаты

Статусы заказа: `pending` → `paid` → `processing` → `shipped` → `completed`, либо `cancelled`.

Правила смены статуса менеджером: `pending → processing | cancelled`, `paid → processing | cancelled`, `processing → shipped | cancelled`, `shipped → completed`. Статус `paid` вручную не ставится. Онлайн-заказ (Click/Payme) нельзя перевести в `processing`, пока он не оплачен. При отмене остатки возвращаются на склад. Заказ с оплатой наличными при `completed` получает `payment_status = paid`. Способ доставки: `courier` (адрес обязателен) или `pickup`. Оплата с баланса пока отклоняется — появится вместе с `balance_transactions`.

1. Покупатель оформляет заказ (`POST /cart/checkout`) → `OrderService` создаёт заказ со статусом `pending`, `payment_status = pending`, фиксирует `price_snapshot` каждой позиции.
2. **Click / Payme** — `ClickPaymentService` или `PaymePaymentService` (оба реализуют `PaymentGatewayInterface`) возвращают фронтенду ссылку на оплату.
3. Провайдер вызывает вебхук `/payments/{provider}/notify`.
4. Сервис проверяет подпись, сохраняет запись в `payments`, ставит обработку в очередь (Redis).
5. Job в DB-транзакции переводит заказ в `paid`. **Статус `paid` ставится только после подтверждения вебхуком**, никогда по редиректу с фронтенда.
6. Менеджеру отправляется уведомление о новом заказе в Telegram (через очередь).
7. Далее менеджер ведёт заказ в админке (`processing` → `shipped` → `completed`).

| 3 | Заказы, корзина, личный кабинет |
| 4 | Платежи (Click/Payme) + вход через Telegram + уведомления |
| 5 | Деплой на VPS, тестирование, запуск |

> Регистрацию мерчанта Click и Payme нужно начать сразу — она занимает 5–14 дней.

---

## 6. Принятые решения

1. **Платформа**: Laravel 13 (PHP 8.4) + Vue 3 SPA, архитектура Controllers → Services → Models, без модулей и CMS.
2. **Аутентификация**: JWT, два изолированных guard'а — `customer` (покупатели) и `api` (персонал).
3. **Вход покупателей**: телефон + пароль (отдельные register/login) или Telegram. Без SMS на 1-м этапе.
4. **Персонал**: `User.role` — PHP Enum `admin` / `manager`, разграничение через role-middleware. Публичной регистрации нет.
5. **Токены**: Access Token 15 минут, refresh-окно 7 дней, встроенные refresh/blacklist `jwt-auth`.
6. **Мультиязычность**: RU/UZ, переводы колонками `*_ru` / `*_uz`.
7. **Заказы**: только для авторизованных покупателей; цена фиксируется в `order_items.price_snapshot`.
8. **Платежи**: Click и Payme через единый `PaymentGatewayInterface`, статус `paid` — только по вебхуку, обработка через очередь Redis.
9. **API**: все роуты с префиксом `/api/v1/`, только JSON, без редиректов.
10. **Mobile-first**: фронтенд проектируется сначала под телефон (320–414px).
11. **Доставка**: адрес и способ указываются при заказе; трекинг — внешний сервис, не входит в 1-й этап.

---

## 7. Открытые вопросы

**Решено:** каталог (товары, категории, фото) доступен и `admin`, и `manager`; управление сотрудниками — любому активному `admin` (отдельной роли «супер-админ» нет). Сотрудник деактивируется полем `users.is_active`; админ не может понизить или деактивировать сам себя.

1. Права `manager` на будущие разделы (финансовая статистика, корректировка баланса).
2. Баланс покупателя: поле `customers.balance` уже есть, но история операций (`balance_transactions`), пополнение и ручная корректировка из админки пока не спланированы.
3. Нужны ли покупателю сохранённые адреса доставки (`customer_addresses`) или достаточно адреса в каждом заказе.

## 8. План развития — подтверждение номера телефона (2-й этап)

На 1-м этапе номер телефона покупателя не подтверждается через SMS — чтобы не тратить деньги на SMS-провайдера при запуске с небольшим количеством клиентов. Схема на будущее:

- Миграцией добавляется поле `customers.phone_verified_at` (nullable, timestamp).
- Администратор в разделе «Клиенты» получает кнопку **«Подтвердить номер»** (например, после звонка клиенту) → эндпоинт `POST /api/v1/admin/customers/{id}/verify-phone` проставляет `phone_verified_at`.
- **Зачем**: подтверждённый номер можно сделать условием онлайн-оплаты (Click/Payme), чтобы снизить риск мошенничества и заказов с нерабочим номером. Покупатели, вошедшие через Telegram, могут считаться доверенными по умолчанию — уточняется отдельно.
- **Когда подключать SMS**: если ручное подтверждение станет неудобным, тот же `phone_verified_at` будет проставляться автоматически после проверки SMS-кода внутри `CustomerAuthService` — изменений в заказах, платежах и фронтенде не потребуется.
